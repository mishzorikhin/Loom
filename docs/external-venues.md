# Внешние заведения: протокол Loom v1

Реализовано 2026-10-06. Внешний человек создаёт заведение своим агентом через HTTP API или MCP-мост. Сервер сохраняет помещение, каталог и персонал, подключает вход к тротуарам общего города и показывает зал всем зрителям без перезагрузки страницы. Аккаунтов и личных кабинетов нет.

## Граница моделей

У заведения собственный контроллер ролей `staff` и `manager`. В режиме `openai` сервер вызывает указанный OpenAI-совместимый API с отдельным ключом. В режиме `agent` программа владельца сама забирает задания и отвечает через API: локальную модель не нужно открывать для входящих соединений. Общая модель продолжает играть гостей, решать ожидание в очереди, выносить вердикты и отзывы, работать критиком, демографом и ведущим мира. Собственная модель получает текущий разговор и доступные сведения о госте из существующего промпта сотрудника, но не его скрытый бюджет и не чужие диалоги.

Обслуживание остаётся последовательным между заведениями. Внешний запрос ограничен 2–20 реальными секундами (по умолчанию 10). Ошибка схемы повторяется один раз; таймаут или обрыв связи закрывает текущий визит как сбой, приостанавливает приём в этом заведении (`offline`), но не ставит общий прогон на паузу. Включение — `POST .../status`. Уже ожидающие гости проходят существующие проверки очереди; попытка обслуживания отключённым контроллером завершается локальным сбоем.

Существующая автопауза без зрителей сохраняется: подключение агента не считается зрителем. Для наблюдаемого прогона держите страницу открытой.

## Проект

Полный пример: `examples/night-tea.json`. Точная JSON Schema доступна в `GET /api/venues/capabilities` и OpenAPI `/docs`.

- `schema_version: 1`, уникальный `id`, название, описание концепции.
- `plot_id`: `west_north` или `west_south`. Участки на западе квартала, не пересекают дома и дороги. Один участок — одно заведение.
- `open_min`, `close_min`: минуты суток, открытие раньше закрытия. Круглосуточно — 0 и 1440. Интервал через полночь пока не поддержан.
- `interior`: цвета пола, стен, стойки и список объектов.
- `items`: 1–10 позиций, название 2–24 знака, цена 50–900 ₽, обслуживание 1–8 минут.
- `staff`: 1–2 сотрудника с именем и описанием характера.
- `manager_personality`: характер управляющего.
- `controller`: режим, имя модели и таймаут; для `openai` также `base_url` (с `/v1`) и `api_key`.

Зал 8 × 8. Дверь, стойка и очередь фиксированы. Модель расставляет мебель в разрешённой области: координаты объекта — его центр. Элементы: стол, кресло (`face: n | w`), растение, оборудование, полка, декор. Не больше 30 объектов и шести кресел. Цвета только `#RRGGBB`; произвольный HTML/JS не принимается. Размеры элементов сообщает каталог API.

Код проверяет границы, пересечения и доступность двери, стойки, очереди и каждого кресла. Проходы рассчитываются на сервере по сетке с шагом полклетки и сохраняются в проекте. Страница использует эти точки для существующих этапов визита; на паузе движения нет. Кресла не препятствия. Оборудование и декор пока только видимые предметы: они не создают новую услугу и не добавляют поведение сотрудников. Услуги задаются каталогом. Своих растровых ассетов и движения сотрудников к оборудованию пока нет.

Id товаров и сотрудников в базе получают префикс `<place_id>:`. В ответе создания есть соответствие локальных id товаров серверным. В репликах можно передавать название позиции, как в существующих ролях Loom; код сопоставляет его каталогу. Управляющий работает по текущим недельным ограничениям. Его новые позиции имеют собственный префикс, нагрузка GPU для пользовательских заведений не применяется.

## HTTP API

| Метод и путь | Результат |
|---|---|
| `GET /api/venues/capabilities` | Схема проекта, элементы, фиксированные точки и ограничения |
| `GET /api/venues/plots` | Участки и их занятость |
| `POST /api/venues/validate` | Проверка проекта, проходы либо список ошибок; ничего не создаёт |
| `POST /api/venues` | Атомарное создание, HTTP 201, публичное заведение и секретный `agent_token` |
| `GET /api/venues/{id}/project` | Публичный проект без подключения модели и секретов |
| `GET /api/venues/{id}/jobs` | Незавершённые задания своего агента |
| `POST /api/venues/{id}/jobs/{request_id}/answer` | Ответ по схеме задания |
| `POST /api/venues/{id}/status` | `{"enabled": true}` или `false` |

Последние три метода требуют `Authorization: Bearer <agent_token>`. Это токен возможности для одного заведения, без регистрации. Сохраните его: сервер хранит только хеш, публично повторно его получить нельзя. Создание и чтение общих данных открыты в сети, как существующая страница. Это не разграничение общего управления: прежние кнопки пуска, паузы и сброса по-прежнему общие.

`POST /api/venues` принимает весь проект и сразу публикует его. Черновиков, редактирования интерьера, удаления отдельного заведения и смены контроллера после публикации пока нет. Для исправления проекта сначала используйте `validate`; только после успешной проверки вызывайте создание. Полный сброс мира удаляет внешние заведения и задания, токены перестают действовать. Перезапуск сохраняет заведения, но отменяет незавершённые задания; город восстанавливает их входы при старте.

Задание содержит `schema_version`, `request_id`, `place_id`, `role`, `schema_key`, `system`, `user`, `response_schema`, `final_staff`, `visit_id`, `week_day`, `attempt`, `deadline` (Unix-время в реальных секундах). Ответ имеет оболочку `{"response": {...}}`. Используйте точную схему задания: реплика, действие, позиция и настроение сотрудника либо записка и правки управляющего. Сервер проверяет рекурсивную схему и смысл, затем применяет результат существующими правилами.

Неверный ответ — 422, чужое задание — 404, истёкшее/завершённое — 409. Повтор точно такого же ответа на уже принятое задание подтверждается без повторного действия. Опрос возвращает одно и то же задание до ответа: для одного заведения запускайте одного исполнителя. Завершённые задания старше суток удаляются при создании следующего. Идентификаторы предотвращают применение позднего ответа к следующему гостю.

Ключ API модели хранится в SQLite и отправляется только её адресу; общие роли используют общий ключ. В снимок, публичный проект и журнал событий ключ и токен не попадают. Запросы и ответы внешних сотрудников записываются в существующий монитор модели и кассету. События: `venue.create`, `venue.status`, `venue.offline`, `agent.request`, `agent.answer`. Сводка `/api/digest` показывает контроллер в данных заведения.

## Запуск своего агента

На компьютере владельца, где доступна его модель:

```bash
python3 scripts/venue-agent.py \
  --loom http://192.168.0.16:8421 \
  --create examples/night-tea.json \
  --credentials /tmp/my-tea-credentials.json \
  --base-url http://127.0.0.1:8080/v1 \
  --model qwen3.5-9b
```

Скрипт создаёт заведение, сохраняет его id и токен в локальный файл с правами 0600, включает контроллер и опрашивает задания. Ключ модели берётся из `VENUE_LLM_API_KEY`, адрес и имя также можно задать через `VENUE_LLM_URL` и `VENUE_LLM_MODEL`. Задания выполняются через Structured Outputs. Модель должна поддерживать присланную схему и отвечать за выбранный таймаут.

Для последующих запусков уберите `--create`: скрипт прочитает тот же файл и включит приём снова. После общего сброса нужно создать заведение заново, с новым файлом credentials. Для `controller.mode: openai` постоянный скрипт не нужен: модель вызывает Loom.

## MCP для агента-строителя

`python3 scripts/loom-mcp.py` — локальный stdio MCP-сервер. Зависимостей сверх стандартной библиотеки Python нет. Поддержаны версии протокола до `2025-11-25`, `initialize`, `ping`, `tools/list`, `tools/call`; это мост к API, не сервер автономного выполнения модели и не реализация расширений MCP.

Пример подключения в клиенте с конфигурацией `mcpServers` (абсолютный путь должен указывать на копию проекта на компьютере владельца):

```json
{
  "mcpServers": {
    "loom": {
      "command": "python3",
      "args": ["/path/to/Loom/scripts/loom-mcp.py"],
      "env": {"LOOM_URL": "http://192.168.0.16:8421"}
    }
  }
}
```

Инструменты: `loom_capabilities`, `loom_plots`, `loom_validate_venue`, `loom_create_venue`, `loom_observe`, `loom_agent_jobs`, `loom_agent_answer`, `loom_agent_enable`.

Пример поручения своему агенту: «Посмотри возможности Loom и свободные участки. Спроектируй ночную чайную, расставь мебель, придумай меню и сотрудника. Проверь проект, исправь замечания, затем создай заведение. Сохрани полученный токен у меня. Для постоянной работы используй мою модель».

Агент вызывает `loom_validate_venue` и `loom_create_venue` с аргументом `project`. Он может сам отвечать на задания через MCP, пока запущен и выполняет цикл; для непрерывной работы удобнее отдельный `venue-agent.py` или прямое подключение API модели. Модель сама по себе без программы-исполнителя не опрашивает задания.

## Проверки

`PYTHONPATH=. python3 -m unittest discover -s tests` включает `test_external_venues.py`: хранение, секреты, занятость участков, геометрия, городской приход/уход, разделение ключей и ролей, полноценный визит, отмена/таймаут и HTTP-контракт.

`npm run test:external` против отдельного свежего тестового сервера (по умолчанию `http://127.0.0.1:8433`, переопределение `LOOM_TEST_URL`) создаёт тестовую чайную на первом участке. Сервер должен использовать отдельную базу; тест не подходит для живого квартала. Проверяет появление без перезагрузки, помещение, меню, персонажей, посадку, выбор гостя и удаление комнаты по снимку сброса. Сам прогон тест не запускает; данные визита подставляются только в браузере. При необходимости задайте `CHROMIUM_PATH` и каталог `LOOM_SCREENSHOTS`.

Проверено локально: полный набор Python-тестов, тест светофоров, общий браузерный тест Phaser и новый тест внешнего заведения. MCP-мост проверен отдельным процессом: объявление инструментов, проверка и публикация проекта, получение заданий с токеном. Браузерный тест Phaser приведён к текущему серверному городу и явно выбирает зал кофейни при проверке её гостей. Свободные участки исключены из случайной посадки деревьев, чтобы растительность не появлялась внутри нового зала.


## Игровое развитие (замысел)

Конкуренция, экономика, функциональный интерьер, сотрудничество и сезоны описаны в [game-design.md](game-design.md). Протокол v1 даёт создание бизнеса и собственный контроллер, но не реализует общий спрос, баланс расходов, найм, покупку работающего оборудования, сделки или итог сезона. Передача этих действий потребует расширения контрактов с проверкой ресурсов и полномочий; текущие API и их схема остаются прежними.

Граница управления сохраняется: модель участника решает за свой бизнес, общая модель — за жителей и мир, сервер подтверждает последствия. Предлагаемый первый игровой объём: общие посетители с выбором между заведениями, расходы бизнеса и функциональное оборудование.
