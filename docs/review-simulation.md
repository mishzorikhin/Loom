## Подтверждённые проблемы и исправления

| Проблема | Последствие | Исправление |
|---|---|---|
| Локальная проверка слабее отправленной схемы; boolean приводился через bool() | Строка `"false"` означает ждать; некорректные вложенные ответы попадали в логику | Рекурсивная проверка той же схемы перед применением, включая кассеты |
| `finish_reason` игнорировался, повтор имел прежний лимит | Обрезанный ответ ошибочно принимался либо повторно обрезался | Обрезание отклоняется, один повтор с удвоением лимита до 4096 |
| Демограф ограничен 900 токенами при пачке до восьми профилей | В журнале два последовательных сбоя JSON ровно по 900 токенов | Базовый лимит 1800; точная причина прежних ответов не сохранена в журнале, связь с обрезанием — вывод по признакам |
| Некорректная оболочка API могла вызвать AttributeError/TypeError | Сбой попадал в общий engine.crash вместо обычной обработки схемы | Явная проверка choices/message/content, обработка refusal |

| Запросы crowd обходили `_thinking` | На ожидании решения толпы часы шли быстрее установленной границы | Общий контекст ожидания модели |
| Кеш толпы учитывал только виды объектов, характер и наличие фактов | Безопасное и опасное окружение, разные факты давали прежнее решение | Ключ включает человека и полное восприятие без времени; истёкшие записи удаляются |
| Сброс не отменял задачи Mind | Ответ старого запроса мог изменить новый город | Отмена и ожидание задач, очистка кеша и наблюдений до сброса |
| Сбой ведущего записывался дважды | Завышенное число ошибок в журнале | Одна запись через Engine._ev |

## Что устроено правильно и ограничения

Запросы действительно используют `response_format={type: json_schema, json_schema: {strict: true, ...}}`, а не только просьбу вернуть JSON в промпте. Схемы закрыты, поля перечислены в required; финальная реплика сотрудника имеет отдельную схему без ask, демограф ЦОДа — свой список характеров и бюджетов. Контекст заведения задаётся ContextVar, поэтому асинхронные задачи не делят один глобальный идентификатор заведения. Цена и исход обслуживания проверяются кодом по каталогу, вердикт гостя ограничивается отдельно; критик не меняет визит. Ошибки важных и необязательных ролей разделены.

Поддержку ограниченного декодирования конкретным сторонним шлюзом нельзя подтвердить одним полем strict в запросе. Локальная проверка обеспечивает контракт на входе симуляции. SO не проверяет смысл истории или реплики: для этого остаются промпты, критик и ограничения действий. Официальное описание различает схему, отказ и преждевременное завершение: [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs).

Регулярки есть в rules.py (имена, токенизация) и engine.py (миграция старой памяти). Парсинга действий из свободной речи регулярками нет. Эвристика echo_ratio и вопросительный знак при serve/refuse могут давать ложные срабатывания; менять их без набора размеченных диалогов было бы неподтверждённой сменой поведения. Город по-прежнему хранится в памяти и теряется при перезапуске; это документированное ограничение. Физический статус закрытия заведения от патча place не имеет собственного срока — открыть его должен следующий патч; срок объекта не открывает заведение автоматически.

## Проверка и эксплуатация

Локально: полный Python unittest и `npm run test:traffic`. Живые LLM тестами не вызываются. Новые проверки воспроизводят неверные типы, вложенные поля, оболочку API, отказ, обрезание, отмену запросов при сбросе и изменение опасности в кеше. Монитор и журнал используют существующий интерфейс.

Исправления выложены на рабочий сервер 192.168.0.16: rsync в /opt/simcheck и docker compose up -d --build. Перед обновлением прогон был на паузе: день 32, 23:58, 31 завершённый визит. После пересоздания контейнера эти значения сохранились, /api/health сообщает app=ok и доступную qwen3.5-9b, /api/digest — ok без flags, страница отвечает HTTP 200. Контрольные суммы llm.py, mind.py и engine.py внутри контейнера совпали с локальными. Старые кассеты с неполными полями потребуется перезаписать. Отдельные диагностические запросы используют текущие настройки модели и сохраняются в мониторе; они не создают визиты и не меняют поток гостей.

Живая проверка после установки: queue — корректный boolean, первая попытка, 898 мс; demographer — восемь профилей, первая попытка, 746 токенов ответа за 21,5 с. Оба ответа прошли локальную схему. Это подтверждает работу выбранных ролей с текущей моделью, но не доказывает отсутствие будущих ошибок или качество всех диалогов.
